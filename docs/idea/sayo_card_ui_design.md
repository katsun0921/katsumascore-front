# サヨ会話UI設計：TOP・リストページのカードから「探す」「要約する」

> ステータス: アイデア（未着手）。HTMLモックで検討中
> 作成: 2026-11-12
>
> モック: [`src/ui-proposals/sayo-chat/`](../../src/ui-proposals/sayo-chat/)（入口は `index.html`、Storybook は `ui-proposals/SayoChat`）
> 会話API: `katsumascore-ai-chat` リポジトリ（Cloudflare Python Workers）。契約の正本は同リポジトリの `schema/`

---

## 1. 概要

KatsumaScore の **TOPページとリストページ（カテゴリ一覧など）** に、AI映画店主「サヨ」への入口を置く。サヨへの問いかけは次の2パターンに分ける。

| | パターン1：おすすめを探す | パターン2：記事を要約する |
|---|---|---|
| 役割 | **検索**。たくさんの記事から、気分や好みに合う作品を探す | **誘導**。タイトルや説明文だけでは記事を開かない人に、記事の中身を短く伝えて記事へ案内する |
| 入口 | ページ上部の「何を観ようか迷ったら」 | 各Postカードの「要約」ボタン |
| 例 | 「怖すぎないホラー」を押す → ホラー作品を最大3本 | 『霧の灯台守』の「要約」を押す → 作品のあらすじと見どころ、向いている人 |

2つのパターンはつながっている。探した結果の各作品から要約へ進み、要約からは「似た作品」を聞ける。

押した後の見せ方は2案ある。どちらにするかは未決（§6・§10）。

- **案D：モーダル**　ページを離れずにその場で開く
- **案E：専用ページ**　`/{locale}/sayo/{記事slug}` などの専用ページへ遷移する

### 1.1 なぜ全ページではなくTOPとリストだけか

- 作品を「選んでいる途中」の人が多いのはTOPとリストである。記事詳細ではすでに記事を読んでいる
- 置き場所を絞ると、表示・費用・回数の影響を見極めやすい
- 全ページ共通のウィジェット（案B）や専用の会話ページ（案A）は、別案としてモックに残している（§11）

## 2. 前提（ai-chat の現状）

UIはこの前提に合わせて設計している。2026-11-12 時点。

| 項目 | 内容 |
|---|---|
| フェーズ | Phase 1a（サヨの限定公開）の準備中。`CHAT_ENABLED=false`、実LLMでの会話は未実施 |
| 公開API | `GET /health`・`GET /avatars`・`GET /assets/{id}/{表情}.webp`・`POST /session`・`POST /message`（すべて `/api/chat/` 配下） |
| 回答の根拠 | KatsumaScore の公開記事を要約した索引だけ。外部の知識は足さない。URLは書かせず、記事カードの値は索引のデータをそのまま使う |
| 応答 | 一括返却（ストリーミングなし）。LLMのタイムアウトは30秒 |
| 回数の上限 | 限定公開時は sid（利用者）30往復/日、IP 60往復/日、サイト全体 $0.50/日。全アバター合算、日付はJST |
| 入力 | 200字まで |
| 記事ごとの要約 | 索引構築時に記事ごとに作り、**人が確認して承認**している（下表） |
| 立ち絵 | 「仮」の印つき画像1枚を5表情に流用中。正式な立ち絵は受領待ち |

承認済み要約（ai-chat `schema/article.schema.json` の `ArticleSummary`）：

| 項目 | 内容 |
|---|---|
| `summarySafe` | ネタバレなしの要約。150〜200字が目安、300字以内 |
| `summarySpoiler` | ネタバレありの要約（本UIでは使わない。ネタバレの許可はサーバーが会話の中で判断する） |
| `moodTags` | 気分タグ1〜3個（例：じわじわ怖い・泣ける・一話完結） |
| `recommendFor` | 向いている人を80字以内の一文で |

**この承認済み要約を表示するだけなら、LLMを呼ばずに済む。** すぐ返り、費用はかからず、1日の回数も減らない。本UIはこれを最大限使い、LLMは「自由入力」と「もっと聞く」に限る。

## 3. パターン1：おすすめを探す（検索）

### 3.1 入口「何を観ようか迷ったら」

TOPページはヒーロー直下、リストページは一覧の先頭（リード記事の上）に置く。

```
┌───────────────────────────────────────────────┐
│ (サヨの顔)  何を観ようか迷ったら                   │
│            サヨ／AI映画店主が、記事から探します      │
│   [怖すぎないホラー] [泣ける作品] [少しずつ観たい] [ワクワクしたい] │
│   [ 気分や好みを自由に（例：雨の日に観たい）  ] [探す] │
│   候補ボタンは記事のタグから探します（回数は減りません）。│
│   自由入力はAIが探します（1回ずつ数えます）。        │
└───────────────────────────────────────────────┘
```

- リストページでは見出しを「映画の中から、何を観ようか迷ったら」のようにし、**そのカテゴリの記事だけを探す**
- 候補ボタンはスマホでは横スクロールにする

### 3.2 2種類の探し方

| | 候補ボタン | 自由入力 |
|---|---|---|
| 仕組み | 承認済み要約の `moodTags` で絞り込む | 既存の `POST /message`（ベクトル検索＋LLM） |
| LLM | 使わない | 使う |
| 回数 | 減らない | 1回ずつ数える |
| 応答時間 | すぐ | 数秒（最大30秒） |
| サヨの返事 | ボタンごとに用意した定型文 | LLMが作る |

結果の画面には、どちらで探したかを表示する。

- 候補ボタン：「**記事のタグから**　回数は減りません」
- 自由入力：「**AIが記事から**　1回使いました（今日あと29回）」

### 3.3 結果の表示

- サヨの返事（1〜2文）と、作品を最大3本
- 各作品には、題名・カテゴリ・スコア・配信先・気分タグと、2つの操作を付ける
  - **要約を聞く** → パターン2へ
  - **レビューへ** → 記事ページへ遷移
- 下に「ほかの気分で探す」として、残りの候補ボタンを並べる
- 見つからないときは、サヨの定型文（`avatar.json` の `noMatch`）を出し、別の言い方を促す

### 3.4 候補ボタンの例（仮）

| ボタン | 絞り込む気分タグ |
|---|---|
| 怖すぎないホラー | じわじわ怖い・ちょっと怖い |
| 泣ける作品 | 泣ける・切ない |
| 少しずつ観たい | 一話完結・会話劇 |
| ワクワクしたい | ワクワク・家族向け |

気分タグの一覧は、ai-chat の要約生成の設定で決まる。ボタンはその一覧と揃える必要がある（§10）。

## 4. パターン2：記事を要約する

### 4.1 カードの「要約」ボタン

| カード | 位置 | 表示 |
|---|---|---|
| TOP：`HomeCard`（160×218 の縦長ポスター） | 画像の右上 | 顔アイコン＋「要約」 |
| リスト：`PostCardImgLeft`（先頭のリード記事） | 画像の右上 | 顔アイコン＋「サヨに要約してもらう」 |
| リスト：`PostCardImgTop`（グリッド） | 画像の右上 | PCは顔アイコン＋「要約」、スマホは顔アイコンのみ |

- 左上はスコア（`ScoreHexBadge`）、右下はVODの印（`VodDots`）で使っているため、右上に置く
- ボタンは丸みのある暗い背景に、ピンク（`--color-accent-strong`）の縁取り。画像の上でも読めるようにする
- 支援技術向けに `aria-label="『作品名』をサヨに要約してもらう"` を付ける

> **カードの構造変更が必要。** 現在の `HomeCard`・`PostCardImgTop` はカード全体が `<Link>` で、リンクの中には `<button>` を置けない。ボタンはリンクの**隣**（兄弟要素）に置き、`position: absolute` で画像の上に重ねる。

### 4.2 要約の中身

```
(サヨの顔)  サヨ／AI映画店主
           『霧の灯台守』は、こんな作品です。          ← 定型の書き出し
           孤島の灯台を一人で守る男が……（summarySafe）

           ┌ こんな方に ──────────────────┐
           │ 大きな音で驚かされるのは苦手だけど…（recommendFor）│
           └────────────────────────┘
           ┌ 気分 ────────────────────────┐
           │ [じわじわ怖い] [静か] [雰囲気重視]（moodTags） │
           └────────────────────────┘
           要約はネタバレなしです。結末まで知りたいときは、下からサヨに聞いてください。

  サヨにもっと聞く（1回ずつ数えます）            今日あと 30 回
  [『霧の灯台守』の見どころをもう少し] [似た作品は？] [惜しいところは？]
  [ この作品について聞く                 ] [聞く]

  [← 前の作品] [次の作品 →]                      [レビューを読む]
  AIの回答です。要約はKatsumaScoreの記事をもとに作成し、編集部が確認しています。個人情報は入力しないでください。
```

- 作品の見出し部分（サムネイル・カテゴリ・公開日・スコア・配信先「〇〇時点」）はカードと同じデータを使う
- **主な操作は「レビューを読む」**。このパターンの目的は記事への誘導なので、いちばん目立たせる
- 「もっと聞く」から先は `POST /message`（LLM・1回ずつ数える）。ネタバレを含むかどうかはサーバーが判定し、`spoiler: true` のときは本文を伏せてから表示する
- 「似た作品は？」の返事に作品が含まれていたら、その作品の要約へ移れるリンクを出す

## 5. 画面の流れ

```
TOP / リスト
  ├─ [何を観ようか迷ったら] ── 候補ボタン or 自由入力
  │        ↓
  │    パターン1：探した結果（最大3本）
  │        ├─ [要約を聞く] ──→ パターン2（「← 結果に戻る」で戻れる）
  │        ├─ [レビューへ] ──→ 記事ページ
  │        └─ [ほかの気分で探す] → パターン1をやり直す
  │
  └─ カードの[要約] ──→ パターン2：要約
           ├─ [レビューを読む] ──→ 記事ページ
           ├─ [前の作品][次の作品] ──→ 同じ並びの作品の要約
           └─ [もっと聞く] ──→ LLMとの会話（似た作品 → 別作品の要約へ）
```

「前の作品／次の作品」の並びは、押したカードが属するセクションの並び（TOPなら「最新レビュー」「高評価」など、リストならページ内の順）とする。探した結果から開いた場合は、その結果の並びとする。

## 6. 押した後の見せ方：モーダル（案D）と専用ページ（案E）

| | 案D：モーダル | 案E：専用ページ |
|---|---|---|
| 形 | PCは画面中央（幅600px）、スマホは下から出るシート（高さ最大90vh） | `/{locale}/sayo/{記事slug}`（要約）、`/{locale}/sayo/search?q=`（探した結果） |
| 立ち絵 | 顔アイコンのみ | PCは左に大きく固定、スマホは上部の帯 |
| 一覧との関係 | 閉じれば元のスクロール位置に戻る。前後の作品へ続けて送れる | 遷移する。「← 一覧に戻る」で戻る |
| 会話を続ける | できるが狭い。長くなると要約が上に流れる | 窮屈にならない |
| URL | 無い（共有・ブラウザの戻るで開き直せない） | ある（共有・戻るができる） |
| 追加の検討 | ほぼ無い | ページ・テンプレートが増える。記事ページと内容が重なるため、検索結果に出さない設定（noindex）を検討。一覧へ戻ったときのスクロール位置の復元 |
| 専用ページの末尾 | — | 「同じ一覧のほかの作品」を横並びで出し、続けて要約を聞ける |

組み合わせる案もある：基本はモーダル、モーダルに「サヨのページで続きを話す」リンクを置き、会話を続けたい人だけ専用ページへ移す。

## 7. 状態ごとの表示

API の `status` と画面の対応。失敗はサヨのせりふではなく、**システムからのお知らせ**として出す（サヨが失敗を「演じる」と、AIの回答と区別しにくくなるため）。

| 状態 | 表示 |
|---|---|
| 読み込み中 | サヨの吹き出しに3つの点（考え中の表情）。要約・候補ボタンは一瞬、自由入力・もっと聞くは数秒 |
| `ok` | 返事と作品を表示 |
| `no_match` | サヨの定型文で謝り、別の言い方を促す |
| `too_long` | 「200文字までで入力してください」。送る前にフロントでも文字数を表示して止める |
| `limit_user` | 「今日の会話回数の上限に達しました。明日（日本時間0時）にまたお話しできます」。入力欄を止める。**候補ボタンと要約は使い続けられる**（LLMを使わないため） |
| `limit_global` | 「サイト全体の上限に達したため、本日の受付を終了しました」 |
| `session_expired` | セッションを作り直す案内 |
| `disabled` | 「ただいま準備中です」 |
| `error` | 「返事を受け取れませんでした」と「もう一度送る」 |
| `spoiler: true` | 本文を伏せ、「ネタバレを含む返事です／表示する」を挟む |

### 7.1 表情の切り替え

API は表情を返さないので、フロントで決める。

| 表情 | 出す場面 |
|---|---|
| `default` | 挨拶、作品の無い返事 |
| `thinking` | 送ってから応答が来るまで |
| `recommend` | 作品が1件以上ある返事、要約の表示 |
| `sorry` | `no_match`・上限・エラーなど `ok` 以外 |
| `secret` | `spoiler: true` の返事 |

モーダル（案D）は顔アイコンだけなので、表情の差は小さい。専用ページ（案E）で立ち絵を大きく出すと、表情の切り替えが活きる。

### 7.2 常に出す注意書き

「AIの回答です」「個人情報は入力しないでください」を常に表示する。ai-chat の Phase 1b（一般公開）の条件でもある。要約には「KatsumaScoreの記事をもとに作成し、編集部が確認しています」を添える。

## 8. フロント実装の方針（案）

### 8.1 レンダリング方式

TOP（ISR）・リスト（ISR）のレンダリング方式は変えない。サヨの部分はすべて**ブラウザからの fetch**（client-side）とする。CLAUDE.md の「TOP：ISR + client fetch」に合う。

専用ページ（案E）を採る場合の方式は未決（§10）。要約は承認済みで変わりにくいためSSGにできるが、要約の取得元（ai-chat の非公開R2）にビルド時に取りに行けるかを確かめる必要がある。

### 8.2 コンポーネント配置（レイヤー規約に沿った案）

| 名前（仮） | レイヤー | 役割 |
|---|---|---|
| `SayoSummaryButton` | `ui-parts` | 顔アイコン＋文言のボタン。表示だけ（`label`・`onClick` を props で受ける） |
| `SayoBubble` | `ui-parts` | サヨの吹き出し（顔・名前・本文） |
| `SayoSummary` | `ui-section` | 要約の表示（書き出し・要約・こんな方に・気分タグ）。データは props |
| `SayoSearchResults` | `ui-section` | 探した結果の作品一覧。データは props |
| `SayoAskBox` | `features/sayo/` | 「何を観ようか迷ったら」の入口。入力の state を持つ |
| `SayoSummaryModal` | `features/sayo/` | モーダルの開閉・前後の作品・もっと聞く（案D） |
| `useSayoSummary` / `useSayoSearch` | `features/sayo/` | 取得と状態の管理 |
| `SayoSummaryTemplate` | `templates` | 専用ページの画面構造（案E）。`PageLayout` でラップ |
| `sayoChat.ts` | `src/libs/api/` | `/api/chat/*` の呼び出しと応答の検証（zod）。components から fetch しない |

- `HomeCard`（`ui-home`）と `PostCardImgTop` / `PostCardImgLeft`（`ui-section`）はロジックを持てないので、ボタンは `features` から**スロット（ReactNode）として渡す**。カード側はスロットを画像の上に配置するだけにする
- スタイルは `ui-parts` が Tailwind、`ui-section`・`features` が SCSS（スタイリング規約どおり）
- 色は CSS 変数経由。モックの暖色（紙・木目・琥珀）を採るなら、`globals.css` にトークンを追加し `Typography.tsx` を同期する
- 文言は各コンポーネントの `i18n.ts` に置く（ja / en）

### 8.3 アクセシビリティ

- モーダルは `role="dialog"`・`aria-modal`、開いたら閉じるボタンへフォーカス、閉じたら押したボタンへ戻す。Esc で閉じる。←→ キーで前後の作品（入力中は除く）
- 応答の表示領域は `aria-live="polite"`
- 3つの点や立ち絵の動きは `prefers-reduced-motion` で止める
- スマホの入力欄は16px以上（iOSの自動拡大を防ぐ）

## 9. ai-chat 側に必要な追加（提案）

ai-chat の規約では、公開JSONの変更は **Schema を先に更新**する。本UIの実装前に、ai-chat 側で次を決めて実装する必要がある。

| # | 内容 | 用途 |
|---|---|---|
| 1 | `GET /api/chat/articles/{id}/summary` … 記事IDで承認済み要約（`summarySafe`・`moodTags`・`recommendFor`）と記事カードを返す | パターン2 |
| 2 | 気分タグとカテゴリで記事を返すAPI（元データは `facets.json` の `moodTags`） | パターン1の候補ボタン |
| 3 | `POST /message` にカテゴリの絞り込みを足すか | パターン1の自由入力をリストページで使う場合 |
| 4 | `MessageRequest` に `articleId` を足すか | パターン2の「もっと聞く」で作品を確実に指定する |

`MessageRequest` は `additionalProperties: true` なので、項目を足しても旧クライアントは壊れない。

## 11. モックと別案

### 11.1 モックの試し方

`src/ui-proposals/sayo-chat/d-card-summary.html` を開く。上部の黄色い帯で次を切り替える。

- ページ：TOP／リスト（映画）
- 押した後：モーダル（案D）／専用ページ（案E）

| 試すこと | 操作 |
|---|---|
| パターン1（候補ボタン） | 上部の「怖すぎないホラー」などを押す |
| パターン1（自由入力） | 「ホラー」「泣ける」「アニメ」「ロボ」などを含めて入力する。それ以外は「見つからない」になる |
| リストのカテゴリ絞り込み | リストで「怖すぎないホラー」を押す（アニメの作品が出ないことを確認） |
| パターン2 | カード右上の「要約」を押す |
| 2つのつながり | 探した結果の「要約を聞く」→ 下の「← 結果に戻る」 |

作品名・スコア・配信先・要約はすべて架空。APIは呼ばず、`card-mock.js` が同じ形の応答を返す。

### 11.3 別案（A〜C）との関係

A〜Cは「サヨと会話する場所」を作る案で、本書の案は「既存の一覧から、目的を絞ってサヨを呼ぶ」案である。本書の案を先に入れ、会話をもっと続けたい人向けに A（専用ページ）を後から足す、という順も取れる。
